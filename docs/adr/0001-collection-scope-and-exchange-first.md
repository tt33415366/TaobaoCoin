# 每日收取的范围限定与「兑换永远优先」的次序

本轮为项目加入每日收取（DailyCollection）与狙击日/收菜日状态机。共四个决策点，全部在实现前确认，此处如实记录。术语见 [CONTEXT.md](../../CONTEXT.md)。

- **Status**: accepted
- **日期**: 2026-10-02

## 决策 1：每日收取只做签到类动作

**背景**：淘金币的日常收益除了红包兑换，还有浏览任务、小游戏、补签等来源。证据来自两处：API 名称与载荷形状从页面 live bundle `@ali/pegasus-project-taobao-signin-game@1.3.2` 提取；开源项目调查（JavisPeng/taojinbi 等）则显示这类工具全部走 UI 自动化（无障碍/控件点击），无一使用纯 API 路径。

**决策**：每日收取只包含三个签到类动作：

1. `mtop.coingame.collect.reward.pc`（签到与收币是同一动作）
2. `pcSign4Sync`（签到状态同步，模仿页面行为）
3. `receivepostpurchasetaocoin`（下单返金币领取）

明确排除：

- **浏览任务**——全 GitHub 无纯 API 路径，需真实页面停留+滚动，是风控画像最重的行为，收益/风险不划算
- **小游戏**——计分在服务端，无法自动化
- **补签**——需要补签卡，不可自动获得

下单返币纳入的理由：领取的是下单时已归属的币，风险与签到同级。

**后果**：三个动作的接口参数均从页面 bundle 逆向、未全部实测，首跑校准点集中在 `gateway.py` 顶部常量（`SIGN_COLLECT_PARAMS` 的 spm、`REWARD_FIELDS` / `BALANCE_FIELD` 金币字段名、`PURCHASE_CLAIM_DATA` 下单返币载荷），`--collect` 即调试入口。

## 决策 2：兑换永远优先

**背景**：收取与兑换共用同一个 cookie 会话，淘宝风控按会话画像——任一侧触发风控，另一侧连坐。

**决策**：

- 狙击日的收取排在兑换流程**正常结束之后**（成功 / 重试耗尽 / 全档周限都算正常结束），时刻天然不规则，不加抖动。
- 兑换路径抛出 `RiskControlBlocked` / `SessionExpired` 当天直接跳过收取，交给外层。
- 收取的任何失败一律只记日志，绝不影响兑换结果与退出码。

**后果**：收菜日当天没有任何兑换请求，收取路径是 cookie 存活的唯一探针——唯独收取发现登录态失效（`SessionExpired`）要在当日摘要中显著标记 🔑，其余失败静默。

## 决策 3：收菜日收取加随机抖动

**背景**：checkin-pilot 的运维记录指出，perfectly regular 的请求时间戳本身是风控特征。

**决策**：收菜日的收取动作在 `run_time` 基础上加 **0–30 分钟随机抖动**（`COLLECTION_JITTER_MINUTES = 30`，常量而非配置项）。两点边界同时钉死：

- 收菜日的**首页探测仍在 `run_time` 准点**——只读、与狙击日同型，抖动只加在收取动作上
- **狙击时刻精度绝不动**，狙击日收取紧跟兑换流程、时刻天然不规则，同样不加

**后果**：收菜日每天的请求时刻不再可预测；代价是收取完成时间散布在 run_time 后 0–30 分钟，当日摘要出现时间相应浮动，属预期行为。

## 决策 4：无跨天状态文件

**背景**：每天 `run_time` 的首页探测（`exchanged_all`）加上级联结果（全档 `WeeklyLimitReached`）已能完整推导当天模式。

**决策**：狙击日/收菜日状态**不持久化**，每天由当天首页数据重新推导；首页权益恢复（新一周）自动回到狙击日。

**后果**：没有状态文件要维护、不会腐化；副作用是收菜日每天在 run_time 仍会有一次首页请求（只读，不消耗兑换机会），换取的是状态永远以服务端为准。

## 修订（2026-10-06，依据 2026-10-02 真实接口探测）

决策 1 的两个事实基础在首跑探测中被证伪，相应修正：

1. **下单返金币（`receivepostpurchasetaocoin`）砍除**。「领已归属的币、风险与签到同级」不成立：`orderIds` 是必填参数，且**只来自支付成功后跳转 URL 的 `bizOrderIds` 深链参数**——淘金币页没有任何查询待领订单的接口（已核遍 bundle 全部调用点与 home/town 真实响应）。自动化它需要先接入交易 API 拉订单号，接口面与风控画像远超签到类，按本 ADR 决策 1 自身的原则排除。
2. **余额与已签判定改走 `mtop.coingame.town.index.get.pc`**。实测确认 `queryTaoCoinHomeV2` 响应**不含余额字段**（原 `BALANCE_FIELD` 猜测作废）；余额在 town 接口的 `model.userInfo.coinAmount`，`model.userSign.signed` 同时给出今日是否已签。

由此带来两个设计红利，一并记录：

- **已签跳过**：每日收取先查 town，已签则记「今日已签到」、不发签到请求（实测已签时 `collect.reward.pc` 返回空 `data`）——「未获得金币」的脏日志消失。
- **收益按余额差计**：+X 取收取前后两次 town 查询的余额差，不再依赖 `REWARD_FIELDS` 对金币字段名的猜测（自报值仅在起始 town 查询失败时兜底）。
